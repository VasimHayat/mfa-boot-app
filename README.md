# MFA Learning App

A Spring Boot 3 + Vue 3 single-page app: password login, TOTP two-factor authentication with
single-use recovery codes, and a filterable learning-module catalog with per-user progress.

Runs entirely offline — no CDN, no npm install, no network at runtime. `mvn package` produces one
runnable jar.

## Requirements

- JDK 21
- Docker, for SeaweedFS — only needed if you want file uploads. Everything else runs without it.
- No Node.js. The frontend is plain ES5-compatible JavaScript served as static files; Vue and
  PrimeVue are vendored under `src/main/resources/static/vendor/`.

## Run

```bash
docker compose up -d
```

```bash
./mvnw spring-boot:run
```

Then open <http://localhost:8080>. Sign in as:

| Username | Password     |
|----------|--------------|
| `demo`   | `Demo@12345` |

The demo user has no authenticator yet, so the first sign-in walks through enrolment: scan the QR
code (or type the setup key) into any TOTP app, confirm with a six-digit code, then save the ten
recovery codes. Those codes are displayed exactly once — only their hashes are stored.

To build and run the jar:

```bash
./mvnw clean package && java -jar target/mfa-learning-app-1.0.0.jar
```

### If Tomcat fails to start

On a locked-down host you may see `Unable to establish loopback connection` at startup. Tomcat's
default NIO connector needs `Selector.open()`, which on Windows is built on an AF_UNIX socket pair
that some sandboxes and endpoint-security products refuse. Start with the NIO2 connector instead,
which uses IOCP:

```bash
java -jar target/mfa-learning-app-1.0.0.jar --spring.profiles.active=nio2
```

## Data

H2, persisted to `./data/mfa-learning.mv.db`, with the schema generated by Hibernate. On an empty
database `DataSeeder` inserts the demo user, twelve modules with lessons, and some partial progress
so the catalog filters and the "Continue learning" card have something to show. Delete the `data/`
directory to start over. The seeder is disabled under the `test` profile.

## Authentication flow

Two-step, with the session upgraded only after the second factor succeeds:

1. `POST /api/auth/login` — verifies the password (BCrypt) and creates a **pre-authentication**
   session holding only `ROLE_PRE_AUTH`. The response says whether the user still needs to enrol
   (`MFA_SETUP_REQUIRED`) or can go straight to a challenge (`MFA_REQUIRED`).
2. `GET /api/mfa/setup` + `POST /api/mfa/confirm` — first-time enrolment. Returns the Base32 secret,
   an `otpauth://` URI and a PNG QR code as a `data:` URI. Confirming issues the recovery codes.
3. `POST /api/mfa/verify` — accepts a TOTP or a recovery code and promotes the session to
   `ROLE_USER`.

A pre-auth session cannot read any learning data; every `/api/**` endpoint outside the auth and MFA
paths requires a fully authenticated session and returns `401 {"error":"mfa_required"}` otherwise.

Security properties worth calling out, each covered by a test:

- **Session fixation** — the session id is rotated on MFA success, so a pre-auth id is never reused
  as an authenticated one.
- **TOTP replay** — the accepted time step is recorded per user; the same code cannot be presented
  twice, even inside its validity window. A ±1 step drift window is allowed.
- **Recovery codes** — 10 per user, BCrypt-hashed, single use. Verifying consumes one.
- **Throttling** — 5 failed verifications locks the account for 15 minutes and invalidates the
  pre-auth session, so a lockout forces a fresh login (`429 {"error":"mfa_locked"}`).
- **Secret at rest** — the shared secret is stored AES-GCM encrypted (`v1:` envelope), never plain
  Base32.
- **Enumeration** — a wrong password and an unknown username produce byte-identical responses.
- **CSRF** — enabled for all mutating requests, token delivered in a readable `XSRF-TOKEN` cookie
  and echoed as `X-XSRF-TOKEN`. A missing token is a `403`, not a `401`, so the SPA does not
  mistake it for an expired session.

### Encryption key

`app.security.secret-key` (see `application.yml`) holds the AES key for the MFA secrets. The bundled
value is a development default. Override it before deploying anywhere real:

```bash
java -jar target/mfa-learning-app-1.0.0.jar --app.security.secret-key="$(openssl rand -base64 32)"
```

Rotating the key makes existing enrolments undecryptable — users would have to re-enrol.

## Catalog

`GET /api/modules` takes `category` (repeatable), `difficulty`, `status` (repeatable), `q`, `sort`,
`page` and `size`. Filters compose with AND; repeated values of one filter are OR'd together.
`status` is evaluated against the caller's own enrollment and accepts `NOT_ENROLLED`, which is the
absence of a row rather than a stored value. Modules can be gated on a role, and a gated module is
absent from the catalog and 404s by slug for users without it.

The interesting constraint is cost: the query is a single JPA Criteria query with a left join to the
caller's enrollment, projecting straight into a DTO, so **a page costs exactly two SQL statements —
one COUNT and one SELECT — regardless of page size**. `CatalogQueryBudgetTest` asserts that with
Hibernate statistics rather than trusting it, because a projection that resolved lesson counts or
enrollments per row would pass every functional test and still fall over on a realistic page.

## File uploads (SeaweedFS)

Signed-in users get a **My files** area where they can upload documents, download them again and
delete them. The bytes go to SeaweedFS; the database keeps only metadata — owner, filename, size,
SHA-256 and the generated storage key.

`docker-compose.yml` runs `weed server` with the master, one volume server and the filer in a single
container. The app talks to the **filer** (`localhost:8888`), whose path-based HTTP API means the app
addresses objects by a key it generates rather than tracking SeaweedFS file ids and doing the
master-assign/volume-write dance itself.

| Endpoint | Purpose |
|----------|---------|
| `POST /api/me/documents` | multipart upload, field name `file` |
| `GET /api/me/documents` | the caller's own files, paged |
| `GET /api/me/documents/usage` | counts, bytes used and the configured limits |
| `GET /api/me/documents/{id}/download` | the bytes, always as an attachment |
| `DELETE /api/me/documents/{id}` | removes the row and the object |

The rules that matter, each with a test:

- **Ownership is part of the query**, not a check after loading, so another user's id reads as 404
  rather than 403 — which also avoids confirming that the id exists.
- **The content type is derived from the extension**, never taken from the browser's claim. A file
  uploaded as `report.txt` with `Content-Type: text/html` is stored and served as `text/plain`.
- **`.html` and `.svg` cannot be uploaded at all.** Served from this origin they would be stored XSS.
  Downloads are additionally always `Content-Disposition: attachment`, with the global `nosniff`.
- **Storage keys are generated** (`/mfa-learning/documents/u{userId}/{uuid}.{ext}`) and validated
  against a strict pattern before every call, so a key can never escape its subtree. The user's
  filename is only ever a download label and is sanitised of paths and control characters.
- **Failed metadata writes delete the object**, so a half-finished upload cannot leak storage.
- **The store being down is a 503**, not a 500 or a validation error, and the UI offers a retry.

Limits live under `app.storage.*` — 10 MB per file, 100 files and 200 MB per user by default.

If you would rather not run Docker, leave SeaweedFS down: the app starts fine and every other
feature works. Uploads will report that file storage is unavailable.

## Frontend

`src/main/resources/static/`, loaded by plain `<script>` tags in dependency order:

```
index.html          shell
app.css             app-specific styles
app.js              API client, history router, PrimeVue registration, view switch
components/         ThemeToggle, LoginView, MfaSetupView, MfaChallengeView,
                    ModulesView, ModuleDetailView, DocumentsView
vendor/             Vue 3, PrimeVue 3 UMD, PrimeIcons, PrimeFlex, light + dark themes
```

Catalog filter state is mirrored into the query string, so a filtered view is shareable, survives a
reload, and is restored intact when Back returns from a module page. Light/dark is a stylesheet swap
persisted in `localStorage`.

Two notes for anyone editing the vendored assets:

- `vendor/primevue.min.js` is assembled from the npm package: `core/core.min.js` first, then the
  per-component UMD files. Order matters, and `base/base.min.js` is deliberately omitted — the file
  header explains why. Do not reorder the blocks by hand.
- The CSP allows `script-src 'unsafe-eval'` because the components declare string templates and
  Vue's in-browser compiler turns them into render functions with `new Function`. Removing that
  relaxation means precompiling templates, which needs the build step this app does without.
  `'self'` still blocks third-party and inline scripts.

## Tests

```bash
./mvnw test
```

44 integration tests against the real HTTP stack and a real H2 database, with a clock the tests
control so the TOTP drift window, the replay guard and the lockout window are deterministic rather
than timing-dependent. No Docker needed: the object store is replaced by an in-memory stand-in that
keeps the same contract.

| Suite | Covers |
|-------|--------|
| `AuthMfaFlowTest` | login, enrolment, verification, replay, recovery codes, throttling, logout |
| `LearningCatalogTest` | filter composition, pagination metadata, role gating, enroll/complete |
| `CatalogQueryBudgetTest` | the two-statement query budget |
| `PreAuthAccessTest` | pre-auth and anonymous access refusal, CSRF, static shell, security headers |
| `DocumentUploadTest` | upload/download/delete, ownership isolation, type and size rules, quotas |

`SeaweedFsClientIT` covers the HTTP calls against a **real** filer and is the one test that proves
the SeaweedFS integration itself. Surefire does not pick up `*IT` by default, so run it explicitly
once the container is up — it skips itself if nothing is listening:

```bash
./mvnw test -Dtest=SeaweedFsClientIT -DfailIfNoSpecifiedTests=false
```
